1. Introducción

1.1 Propósito del documento

El presente Documento de Arquitectura de Software (SAD) describe la estructura técnica del sistema SmartAssign, siguiendo las guías del estándar ISO/IEC 42010:2022 (descripción de arquitectura de sistemas) y utilizando el Modelo C4 (Context, Containers, Components, Code) para organizar las vistas arquitectónicas. La notación gráfica se basa en UML 2.5.

Este documento está dirigido a: arquitectos de software, analistas de sistemas, supervisores de ingeniería, y equipos de desarrollo y mantenimiento.

1.2 Alcance del sistema

SmartAssign es una aplicación que automatiza la asignación de personal operativo a celdas de trabajo en una planta industrial de licores. El sistema gestiona:

  • Inicio de turnos con pre-asignación automática de operarios fijos (Operador A, Averiero, Operador C).
  • Asignación manual mediante escaneo QR del gafete del operario.
  • Validación de restricciones médicas, incompatibilidades entre compañeros y reglas de fatiga ergonómica (24h).
  • Relevos ergonómicos en cascada con tránsito inter-líneas por prioridad.
  • Monitoreo en tiempo real del estado de la planta desde múltiples terminales simultáneas.

1.3 Restricciones arquitectónicas

Restricción Absoluta

Toda la base de datos y la arquitectura en la nube funcionan exclusivamente con Firebase (Firestore). No se utiliza SQL, C#, ni backend propio. La lógica de negocio se ejecuta en el cliente mediante transacciones atómicas del SDK Firebase v10+.

7.2 Reglas de seguridad de Firestore

Las reglas de seguridad (firestore.rules) implementan una validación de máquina de estados en el servidor, garantizando que ningún cliente pueda escribir un estado inválido.

puestos Libre Condicional status debe ser uno de 4 valores: VACANTE, ASIGNADO, ALERTA_VACANTE, SUSPENDIDO.

8. Decisiones Arquitectónicas y Justificación

Las siguientes decisiones de diseño fueron tomadas considerando las restricciones del proyecto, el contexto industrial y los recursos disponibles del equipo.

IDDecisiónAlternativa descartadaJustificación
AD-01 Lógica de negocio en cliente con transacciones Firestore Cloud Functions de Firebase El plan actual de Firebase no incluye Cloud Functions. Las transacciones atómicas del SDK (runTransaction) garantizan integridad ACID sin backend dedicado.
AD-02 Caché persistente con IndexedDB multitab Sin caché (solo online) La planta industrial tiene zonas con WiFi intermitente. El caché persistentLocalCache permite operación degradada sin perder datos.
AD-03 Empaquetado Android con Capacitor React Native / Flutter Capacitor permite reutilizar el 100% del código React existente. El equipo ya domina React; no se justifica aprender un framework nativo.
AD-04 Sincronización en tiempo real con onSnapshot() Polling periódico con getDocs() Los tableros de planta requieren actualización instantánea. onSnapshot() proporciona latencia de ~200ms vs. polling de 5-15s.
AD-05 CSS-in-JS con Stitches (zero-runtime) TailwindCSS / CSS Modules Stitches genera CSS en tiempo de compilación (zero-runtime overhead), ideal para dispositivos Android de gama media en la planta.
AD-06 Guard de conectividad como módulo separado Lógica inline en cada componente Centralizar la detección de red en un solo módulo evita duplicación y garantiza comportamiento uniforme en toda la UI.
Registro de decisiones arquitectónicas (ADR).

9. Glosario de Términos

TérminoDefinición
Bolsón (L8)Línea 8 de la planta. Funciona como pool de operarios disponibles que no están asignados a ninguna línea productiva.
Celda operativa / SlotPuesto de trabajo individual dentro de una línea de producción (ej. "L4-Llenado-01").
Intercepción en calienteMecanismo que redirige a un operario recién escaneado hacia una línea de mayor prioridad que tiene vacantes, en lugar de asignarlo a la línea actual.
Rastro DualPatrón de registro que mantiene la referencia al titular planificado (idWorkerOriginal) cuando un reemplazo ocupa su puesto por ausencia.
Relevo ergonómicoSustitución de un operario que ha superado el umbral de esfuerzo físico continuo, para prevenir fatiga y lesiones.
CascadeoCadena recursiva de reubicaciones: cuando un operario es relevado, el sistema busca dónde reubicar al relevado, potencialmente generando otra reubicación.
SKUStock Keeping Unit. Código de producto que determina qué puestos se activan en cada línea y con qué configuración.
Fase de ArranquePrimeros 10 minutos del turno. El aislamiento impide desvíos de operarios entre líneas para garantizar estabilidad inicial.
Fase de MarchaPeriodo posterior al arranque donde se habilitan las interceptaciones en caliente y los relevos inter-líneas.
Guard de ConectividadMódulo que detecta la pérdida de WiFi y activa el modo defensivo: bloquea escaneo QR y congela transferencias inter-líneas.
